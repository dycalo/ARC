# ARC v0.1 runtime specification

This document specifies the supported interfaces, state transitions, and operating limits of ARC v0.1. The [runtime guarantees](assurance.md) describe the execution boundary and failure behavior; the [release procedure](release.md) describes validation and installation checks.

The product is one npm package, `@dycalo/arc`, with an `arc` workspace launcher and standalone runner, public core exports and the `@dycalo/arc/dsh` plugin entry. Source is divided into `packages/core/src`, `packages/cli/src` and `packages/dsh/src`, built together into `dist`. Internal imports use relative paths such as `../../core/src/index.js`; there are no separately published workspace packages. Node 22.19+ is required for the built-in SQLite store. DSH integration targets the published npm release `0.1.2-rc.1`.

The launcher provides `arc setup`, `arc web`, `arc exec`, and `arc harness status`. Setup installs a private, pinned DSH toolchain and workspace-specific profiles; subsequent launches perform readiness checks without installation. It saves the selected mode and runtime settings, preserves existing settings on repair, and prevents concurrent setup or execution within one workspace. Generated profiles bind sessions to the workspace real directory before input admission and tool dispatch. This check controls session routing and does not sandbox native tools. The [harness guide](harness.md) and [configuration guide](configuration.md) document these commands separately from the standalone runner.

The launcher also accepts `arc setup --context-config FILE` for runtime, native interface, checkpoint, progress memory, requirements, activity, incomplete-response recovery and provider-neutral request settings. It validates the effective policy with the same parser used by the plugin before installation, saves explicit values and reports effective defaults. File values override saved fields; explicit flags override file fields. Runtime settings merge by field, while a supplied progress-memory object replaces the previous object. Repair and launch do not reread the source file. Both Web and headless profiles bind the saved policy.

The shared interface is `packages/core/src/types.ts`. `ArcRuntime` implements `ArcRuntimeInterface`; it and `DEFAULT_CONFIG`, `DEFAULT_CONTRACT`, `ArcError`, `parseProposalInput`, `parseContract` and `parseConfig` are exported from core `index.ts`.

- `new ArcRuntime({ databasePath, config?, contract? })` opens/creates the durable store. A supplied contract on an existing store must match; changes go through explicit version-checked `updateContract`.
- `createSession(task, id?)`, `getSession`, `listSessions` handle tasks. Every session has separate requirements and memory; managed resources are shared within one database.
- `observe(sessionId, input)` adds immutable, versioned tool/user evidence, optionally with managed resource dependencies. Updating an explicit record id invalidates old views referencing it. Do not ingest model text as authoritative user instructions.
- `putResource(key, value)` models an external managed-state update, including same-value writes advancing the version. `getResource` returns its version. Requirements for a managed resource use `resource:<key>`; record requirements use the record id returned by observe. The task is always mandatory.
- `prepare(sessionId)` builds a bounded, deterministic View, creates a new invocation/certificate, and advances the actor-call counter. Window policy reuses the requirement plan/candidate identifiers while freshness and current input admission are checked on every call. It never reuses an invocation certificate. A new preparation supersedes outstanding proposals for that session.
- `verify(preparedInvocation)` rejects modification, stale dependencies or contract versions. `propose(invocation.id, {action,requirements,additionalResources?})` validates model JSON and seals a single-use proposal. An invocation can create at most one proposal. `commit(proposal.id)` rechecks and atomically applies managed action, consumes proposal and activates requirements; rejected actions do not change active requirements or managed resources. Retrying a consumed/rejected proposal never applies it again.
- Managed actions are `set`, `remember`, `forget`, `recall`, `propose_contract`, `noop`, `finish`. `set` modifies a SQLite-managed key/value resource, not arbitrary files or an external service. `remember` writes source-labelled candidate memory; `forget` retires model memory but never domain obligations. `recall` admits bounded, source-dependent search results. `propose_contract` stores a candidate which only a trusted host can apply. `finish` records completion. Their atomic guarantee is limited to this database and trusted runtime.
- `getRecordCommit(sessionId, { id?, version?, source? })` reads a committed `remember` action and its original invocation and record. An ID or source is required; an exact version additionally requires an ID. This historical, read-only result does not make the old invocation current or admit an old record into a new View.
- Trusted adapters can seal an external operation plan, claim ordered operations, record results and settle the complete batch. The external journal atomically consumes its plan and activates requirements; it does not apply or roll back external effects. Pending/unknown plans block another preparation until settlement or host reconciliation. See [native execution](native-execution.md).
- Record dependencies are transitively closed. Optional stale/expired observations are omitted; required stale/missing evidence fails admission. Memory is per session, bounded in active entry count, with optional TTL in actor steps. Mandatory evidence is never silently truncated.
- Requirements scopes are `step` (one subsequent invocation), `window` (the next `horizon` invocations after activation), and `session` (until explicitly retired). Window requirement lifetime is independent of the candidate-cache refresh interval. Required wins over optional, full over summary over metadata. A new declaration activates only after successful managed commit. Contracts supply mandatory resource requirements independently of model declarations.
- Host preparation may also supply `serializedViewBudgetBytes`, an exact allowance for `JSON.stringify(view.rendered)`. The compiler fits both limits and the independent verifier rechecks them; the saved invocation snapshot binds the allowance across restart. Optional previews can fit without weakening required fidelity.
- Host `observedRecords` must be present and receive full detail before optional archive material, with source previews permitted under pressure. An explicit requirement retains its fidelity; flexible observed representations are protected in the saved invocation snapshot. Host `candidateRecords` orders or filters undeclared optional candidates, never mandatory or explicitly declared evidence.
- `captureResponse(invocationId, text, { maxBytes?, ttlSteps?, excerpt? })` captures host-supplied model response text before action sealing as optional model memory. It binds the originating invocation and all admitted source versions/expiry, labels the text unverified, and neither consumes a proposal nor activates requirements. Memory permission, live host conditions and entry limits apply; disallowed or full-capacity capture returns no record. Capturing is a host ingestion operation, separate from the action transaction.
- Budgets are exact UTF-8 bytes of the canonical rendered View, labelled as bytes, not falsely reported as exact model tokens. CLI and DSH add separate whole-request limits for system, tools and protocol overhead. All returned certificate fields are bound to authoritative runtime state; certificates are never model authority.
- Optional `viewFormat: text` renders the same selected records and requirements as source-preserving fenced sections. Omission preserves the original JSON rendering and configuration identity. Both formats use the same independent source verification and exact byte budgets; changing format requires fresh preparation.
- In text mode, DSH also ingests new declarative native text results as lossless fenced source blocks with explicit tool, arguments, execution status and block metadata. Other blocks retain JSON; existing observations keep their original representation. The core treats either encoding as an opaque source string and retains its independent budget and fidelity verification.
- Declarative DSH may pin a bounded host observation of recent journaled native returns. `recentActivityLimit` defaults to four and accepts 0–16; zero disables it. Preparation count and operation status describe execution history, not current file state or task correctness. Each prepared step has a distinct snapshot identifier; historical snapshots remain archived and excluded from undeclared candidates. All snapshot bytes count toward the same input budgets, and model-memory dependency/expiry rules remain unchanged.

Evidence selection first measures the complete mandatory rendering, then admits explicit optional requirements. Adaptive allocation covers undeclared optional records using eligible source-backed previews before upgrading them to full detail when capacity remains. The full-only policy disables that preview allocation. Explicit fidelity requirements are preserved; reduced records are labelled. Once selected, the View presents the task first, managed snapshots by identifier, and observation/memory versions in database write order. The verifier independently checks representation and order against stored sources. Write order describes runtime ingestion, not external event time or filesystem freshness; sorting does not add or remove evidence or change its exact byte cost.

Optional `maxOptionalRecords` (0–1,024) bounds admitted undeclared archive fill in candidate order. Mandatory evidence, host observations and explicit optional requirements remain outside this count. Missing, stale, expired, duplicate or unfit candidates consume no slots. The compiler retains selected detail when it fits; independent admission checks the count as well as the existing source and byte constraints. Omission preserves prior configuration identity. No archive records or memory lifetimes are changed.

Declarative DSH candidate order starts with the two newest progress records, then other archive evidence, then older progress. Actual source eligibility and all explicit requirements remain under core admission. This ordering does not overwrite or retire historical progress and adds no model call.

Preparation permits a configured 1–4 candidate materialization attempts, default two, within the same SQLite snapshot. Recovery rebuilds the candidate set from authoritative sources and independently verifies it again. It does not issue an extra invocation, advance requirement expiry, call the actor or repair an already rejected actor proposal. Persistent failures roll back preparation. Resource localization currently uses exact record/managed-resource identifiers and adapter-bound future-result aliases, not a general semantic search index. Unresolvable required references are rejected before proposal sealing and checked again at activation, including references retired by the action. Existing archived records and action-created results remain addressable; this check does not establish future freshness or budget feasibility.

The standalone runner supports an offline managed-action demo and a DeepSeek-compatible provider loop. Credentials are read from environment and never written to config/store. File tools stay within a selected workspace and are guarded before dispatch; they do not inherit managed-database atomicity. Default run has no unrestricted shell. File actions retain noop permission and live contract precondition checks, then use the core external journal to bind future results and settle requirements. Confirmed recorded outcomes can settle on resume without file replay; uncertain dispatches require host reconciliation. Their external effects and ARC state changes are separate operations, as described in the [CLI documentation](cli.md).

The DSH plugin replaces historical model input with the admitted View by default, accounts for pending messages and runtime context, exposes typed ARC tools, and manages its own durable store. Its integration tests run the supported DSH packages. Recovery uses ARC's durable task binding and observations; missing or inconsistent retained tool results stop recovery before model dispatch. The plugin supports a `context` profile for native tools and a `governed` profile restricting execution to ARC managed tools. Governed mode rejects unsupported actions.

Optional declarative `nativeHistorySteps` (0–8, default zero) retains a contiguous suffix of complete original native assistant/tool events. It requires returned-reasoning capture. Complete serialized assistant messages use the existing response-memory interface and capture cap; unsupported or oversized messages fall back to ordinary excerpt capture. Only full, currently admitted original capture and host receipt records can support retained events. Candidate selection reserves their exact serialized message bytes from the separate request allowance. If that reservation prevents mandatory admission, the host drops the optional window and retries preparation once; the failed preparation advances no actor step. A fresh certificate and the full assembled-request gate still apply. Restart, new user input and managed actions reset native conversation retention without replaying effects. Core remains independent of DSH and the database schema is unchanged.

Declarative DSH captures visible response text by default. Optional `progressMemory.includeReasoning: true` adds provider-returned reasoning, labelled unverified, after visible text within the same total UTF-8 capture allowance. The adapter passes this text through `captureResponse`; dependency, expiry, memory permission and View/request limits remain runtime-owned. Optional `progressMemory.excerpt: head-tail` uses the core capture policy to retain both response endpoints with an explicit middle-omission marker inside the same UTF-8 excerpt allowance. The complete source-text digest remains recorded; omission/default `prefix` preserves the earlier payload format. No extra model call is made and reasoning is never appended outside the admitted View. Existing captures retain their lifetimes when new capture is disabled.

The optional declarative-native `incompleteResponseRetries` allowance defaults to zero and is bounded at eight per ARC task. Unattended hosts may enable it to recover a prose-only response through DSH's public stopping boundary. Ordinary prose uses next-step steering; output-limited prose uses a new DSH turn to clear its retained `max-tokens` ending. The ARC task and durable allowance remain the same. Tool-call stream blocks exclude recovery even when DSH discards them from the assembled message. A persisted host notice enters the next admitted View; each recovery needs a fresh invocation and preserves normal limits. Exhaustion leaves the task active with an explicit error. Cancellation, native turn conclusion and provider failure do not trigger this path; no action or declaration is inferred from text.

Tool observations bind a unique preceding call by turn, step and call ID. Native context observations carry the original tool name and arguments with the result; managed payloads carry an arguments digest to avoid reviving stale evidence. Recovery refuses legacy result-only observations rather than inventing missing bindings. Generated context profiles also use smaller native read, shell and search previews; tools retain their own truncation notices and ARC still checks the complete observation budget.

Each DSH View includes the complete active contract in a mandatory host-owned evidence record. Identical rules retain their record version; changes update it before admission. A concurrent contract change between observation and preparation is refused before model dispatch. The contract text counts toward the View budget and cannot be replaced by model memory.

New context installations expose `arc_step` for native operation/requirements batches and `arc_act` for managed actions. Native tools remain in the DSH registry and execute through its public policy pipeline. Local result aliases bind to runtime-allocated records. The next pre-step settles the final persisted DSH receipt before preparing a new invocation. It admits deterministic result previews as observed requirements, including failed-batch observations. Declared full requirements remain authoritative. No model checkpoint is required. The optional `nativeMode: declarative-tools` interface instead exposes individual native wrappers with original top-level arguments and `arc_requirements`, using the same dispatch and settlement machinery. Legacy `nativeMode: direct` retains the earlier tool surface and optional checkpoint workflow.

Optional DSH `requireNativeRequirements: false` applies only to `nativeMode: declarative-tools`. An omitted native array means no new requirements, equivalent to `[]`, without renewing existing windows. Supplied arrays remain validated before effects; core plan settlement, contract obligations and fresh certificates are unchanged. Omitting this setting preserves the original strict schema. New-call policy changes do not reinterpret the binding or effects of an already sealed native plan.

The individual-tool interface accepts up to 16 native calls per response in one sequential external plan. Whole-response preflight precedes effects; every final outer receipt is bound to settlement before combined requirement activation. A managed action remains a separate response. Existing single-tool and `arc_step` plans keep their recovery formats; multiple individual calls use a distinct adapter binding without a database migration.

The optional DSH `checkpointEveryNativeSteps` setting (0–128, default zero) enforces a context-mode cadence. A due phase restricts the next invocation to managed checkpoint/completion work; safe memory retirement cannot reset the counter. Checkpoints use fresh IDs, full required step declarations, and subsequent host-required retention. The policy's phase is itself admitted evidence, and recovery derives checkpoint success from the existing SQLite commit. The feature has no DSH-specific core state or schema migration and is independent of ordinary requirement-window length. See [checkpoint behavior](dsh.md#scheduled-progress-checkpoints).

The due-phase schema makes the required memory fields and eligible sources explicit while keeping actual IDs in the admitted View. Errors distinguish unavailable sources, user input, host policy and ARC receipts without reading archive text. In the normal DSH loop, the next model request can correct a rejected declaration using its fresh invocation and current View. An argument rejection before proposal creation does not consume the existing invocation; source checks, multi-source support and atomic commit remain unchanged.

The `@dycalo/arc/web` companion and browser client customize the official DSH brand slots and expose an authenticated, read-only workspace overview. They reuse the mounted `ctx.arc` controller. Status reads never open another runtime, prepare an invocation, or apply a contract; recent per-session invocation metrics are limited to the current process. The browser keeps the official chat and settings interfaces, with an added ARC overview accessible from the sidebar and settings.

Release checks cover build/typecheck, core failure and recovery behavior, CLI offline and mocked-provider operation, the DSH loop, packed installation, lockfile reproducibility, and supported Node versions in CI. English and Chinese onboarding document the operating limits. A remote-provider smoke runs only when a provider credential is available; its result is reported separately from offline checks.

The optional `@dycalo/arc/eval` entry exports a standalone SQLite budget ledger and a restricted Flash proxy. It has no DSH dependency and does not attach automatically to launcher sessions. Repository evaluation scripts compose it with the pinned DSH app, isolated task containers and an official SWE-bench grader. Paid execution requires a separate explicit CLI flag; preflight and synthetic-provider modes make no model calls. Its financial reservations are separate from View admission and managed-action transactions.

Each repository evaluation run may select an output-token ceiling from 1 to 16,384, with the existing 16,384 default. The driver configures actor and compaction limits and checks requests before dispatch; the host gateway independently enforces the selected ceiling. Reports retain these settings. A smaller allowance changes the reservation and possible output length, without relaxing the money or input boundaries.

Evaluation runs may independently set a complete input-byte ceiling, an ARC View ceiling and an off/low/high/max reasoning mode. The gateway enforces the selected mode and exact canonical wire-message/tool bytes for actor and auxiliary calls before reserving funds, and records admitted input sizes before forwarding. Raw DSH uses native compaction with a configured heuristic threshold; ARC uses its View materializer. These limits do not substitute output length or cumulative spending for input capacity. Historical configurations retain their defaults.

Each evaluation run retains separate actor-package and host-only grading-input snapshots. The latter contains the manifest, dataset, image lock, grading wrapper and test-service helper, with identity checks before task startup and grading. Shared runtime binaries and lockfiles have explicit drift checks; full installed environments remain host-managed. Validation failures after actor execution retain the actor outcome, patch identity and budget record while refusing an unverified score.

Version 2 evaluation image locks may explicitly enable a fixed, bounded httpbin TCP relay for an instance's existing tests. Both actor and grader retain Docker network mode `none`, the same image and original CA bundle. A separate host process provides this declared external dependency without receiving provider credentials. Version 1 locks cannot enable it. Identity checks, failure-driven actor cancellation and final connection accounting are separate from model completion and official test scores; external service behavior is not frozen.
