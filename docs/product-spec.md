ARC v0.1 release scope

This is the implementation and acceptance specification. Features become release claims only after their automated checks pass.

The product is one npm package, `@dycalo/arc`, with a standalone `arc` CLI, public core exports and the `@dycalo/arc/dsh` plugin entry. Source is divided into `packages/core/src`, `packages/cli/src` and `packages/dsh/src`, built together into `dist`. Internal imports use relative paths such as `../../core/src/index.js`; there are no separately published workspace packages. Node 22.19+ is required for the built-in SQLite store. DSH integration targets the installable npm release `0.1.2-rc.1`, not the newer unpublished research snapshot.

The shared interface is `packages/core/src/types.ts`. `ArcRuntime` implements `ArcRuntimeInterface`; it and `DEFAULT_CONFIG`, `DEFAULT_CONTRACT`, `ArcError`, `parseProposalInput`, `parseContract` and `parseConfig` are exported from core `index.ts`.

- `new ArcRuntime({ databasePath, config?, contract? })` opens/creates the durable store. A supplied contract on an existing store must match; changes go through explicit version-checked `updateContract`.
- `createSession(task, id?)`, `getSession`, `listSessions` handle tasks. Every session has separate requirements and memory; managed resources are shared within one database.
- `observe(sessionId, input)` adds immutable, versioned tool/user evidence, optionally with managed resource dependencies. Updating an explicit record id invalidates old views referencing it. Do not ingest model text as authoritative user instructions.
- `putResource(key, value)` models an external managed-state update, including same-value writes advancing the version. `getResource` returns its version. Requirements for a managed resource use `resource:<key>`; record requirements use the record id returned by observe. The task is always mandatory.
- `prepare(sessionId)` builds a bounded, deterministic View, creates a new invocation/certificate, and advances the actor-call counter. Window policy reuses the requirement plan/candidate identifiers while freshness and current input admission are checked on every call. It never reuses an invocation certificate. A new preparation supersedes outstanding proposals for that session.
- `verify(preparedInvocation)` rejects modification, stale dependencies or contract versions. `propose(invocation.id, {action,requirements,additionalResources?})` validates model JSON and seals a single-use proposal. An invocation can create at most one proposal. `commit(proposal.id)` rechecks and atomically applies managed action, consumes proposal and activates requirements; rejected actions do not change active requirements or managed resources. Retrying a consumed/rejected proposal never applies it again.
- Managed actions are `set`, `remember`, `forget`, `recall`, `propose_contract`, `noop`, `finish`. `set` modifies a SQLite-managed key/value resource, not arbitrary files or an external service. `remember` writes source-labelled candidate memory; `forget` retires model memory but never domain obligations. `recall` admits bounded, source-dependent search results. `propose_contract` stores a candidate which only a trusted host can apply. `finish` records completion. Their atomic guarantee is limited to this database and trusted runtime.
- Record dependencies are transitively closed. Optional stale/expired observations are omitted; required stale/missing evidence fails admission. Memory is per session, bounded in active entry count, with optional TTL in actor steps. Mandatory evidence is never silently truncated.
- Requirements scopes are `step` (one subsequent invocation), `window` (the next `horizon` invocations after activation), and `session` (until explicitly retired). Window requirement lifetime is independent of the candidate-cache refresh interval. Required wins over optional, full over summary over metadata. A new declaration activates only after successful managed commit. Contracts supply mandatory resource requirements independently of model declarations.
- Budgets are exact UTF-8 bytes of the canonical rendered View, labelled as bytes, not falsely reported as exact model tokens. CLI and DSH add separate whole-request limits for system, tools and protocol overhead. All returned certificate fields are bound to authoritative runtime state; certificates are never model authority.

The CLI must support an offline managed-action demo and a real DeepSeek-compatible provider loop. Credentials are read from environment and never written to config/store. File tools stay within a selected workspace and are explicitly pre-dispatch guarded only; they do not inherit managed-database atomicity. Default run has no unrestricted shell. External tool action envelopes may use a checked core noop transition to activate the next declaration after success, but their weaker external-effect guarantee must remain explicit.

The DSH plugin must replace historical model surface, account for pending messages/runtime context, expose typed ARC tools and manage its own durable store. It must use real DSH packages in an integration test. Unknown critical custom Session events cannot be relied on for default DSH replay. The plugin supports a context profile for native tools and a governed profile restricting execution to ARC managed tools; strict mode cannot silently downgrade unsupported actions.

Release gates: clean build/typecheck, core failure/recovery tests, CLI offline and mocked-provider tests, DSH real-loop integration tests, packed-install smoke, reproducible lockfile, CI and complete English/Chinese onboarding with assurance limits. A remote-model smoke runs only when a provider credential is explicitly available; offline tests must not imply live-provider validation.
